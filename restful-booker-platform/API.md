# Restful Booker Platform — API Reference

The Swagger pages generated by the services list paths and schemas only: the source has no OpenAPI annotations, so there are no descriptions, auth rules or error codes. This reference fills that gap.

**How it was built:** from the source code (`*Controller.java`, `*Service.java`, model classes, Next.js `src/app/api/**/route.ts`), then every status code below was **observed against the local stack** (image tag `latest`, 2026-07-01). Where the code and the running app disagree, this doc reports what the app actually does and flags it with ⚠️.

---

## 1. Overview

Every API can be called two ways:

| Way | Base URL | Notes |
|---|---|---|
| **Direct** (recommended for API testing) | `http://localhost:<port>/<svc>` | The real service. Everything in sections 4–9 describes this. |
| **UI proxy** | `http://localhost:3003/api/<svc>` | The Next.js layer the website uses. It **changes status codes and bodies** — see [section 10](#10-ui-proxy-apiservice-differences). |

| Service | Direct base URL | Purpose |
|---|---|---|
| auth | `http://localhost:3004/auth` | Login, token validation, logout |
| room | `http://localhost:3001/room` | Room catalogue |
| booking | `http://localhost:3000/booking` | Reservations |
| message | `http://localhost:3006/message` | Contact-form messages (admin inbox) |
| branding | `http://localhost:3002/branding` | Hotel name, contact details, map, logo |
| report | `http://localhost:3005/report` | Calendar data built from rooms + bookings |

Supporting endpoints on every service: `/actuator/health`, `/swagger-ui/index.html`, `/v3/api-docs`.

Paths take an optional trailing slash: `/room/` and `/room` behave the same for collection endpoints.

## 2. Authentication

1. `POST /auth/login` with `{"username":"admin","password":"password"}`.
2. The **direct** service answers `200` with an **empty body** and a `Set-Cookie: token=<16 chars>; Path=/` header. (The UI proxy instead returns `{"token":"..."}` in the body.)
3. Send the token as a cookie on protected calls: `Cookie: token=<value>`.

Rules (all verified):

- **Missing or invalid token → `403 Forbidden`**, never 401. Each service checks the token by calling `POST /auth/validate`.
- **Validation runs before the auth check.** A protected `POST`/`PUT` with an invalid body returns `400` even with no token.
- **Tokens do not expire.** A 1-hour expiry is written to the database (`Token.createExpiryTimestamp`), but `/auth/validate` never checks it. A token stays valid until `/auth/logout` or a data reset (`make reset`).
- Multiple tokens can be active at once; each login issues a new one.

Which endpoints need a token:

| Service | Public | Token required |
|---|---|---|
| room | `GET /`, `GET /{id}` | `POST /`, `PUT /{id}`, `DELETE /{id}` |
| booking | `POST /`, `GET /summary`, `GET /unavailable` | `GET /`, `GET /{id}`, `PUT /{id}`, `DELETE /{id}` |
| message | `GET /`, `GET /count`, `GET /{id}`, `POST /` | `PUT /{id}/read`, `DELETE /{id}` |
| branding | `GET /` | `PUT /` |
| report | `GET /room/{id}` | `GET /` (see [report](#9-report) for its odd failure codes) |

> ⚠️ Message **reads** (`GET /message/`, `GET /message/{id}`) are public on the service even though they're shown only in the admin area. The UI proxy adds a cookie check on `GET /api/message/{id}`, but the service itself doesn't.

## 3. Error responses

**Validation failure (`400`)** on room, booking, message and branding bodies:

```json
{
  "errorCode": 400,
  "error": "BAD_REQUEST",
  "errorMessage": "Validation failed for argument [0] in public ... (long Spring message)",
  "fieldErrors": ["size must be between 3 and 18"]
}
```

`fieldErrors` holds one human-readable message per broken rule. The messages come from the model annotations, so some are custom ("Firstname should not be blank") and some are Spring defaults ("size must be between 3 and 18").

**Other errors** use Spring's default body:

```json
{"timestamp":"2026-10-17T16:15:45.067Z","status":500,"error":"Internal Server Error","path":"/room/999"}
```

You get this shape for:
- malformed JSON
- an unparseable date (`400`)
- a missing required query parameter (`400`)
- unhandled server errors (`500`)

**Non-numeric IDs** (`/room/abc`) don't match the `{id:[0-9]*}` route pattern, so they return `404`.

**Success responses with no body:** `DELETE` and `PUT /message/{id}/read` return a status only.

## 4. auth

| Method | Path | Purpose | Auth | Success |
|---|---|---|---|---|
| POST | `/auth/login` | Exchange credentials for a token cookie | – | 200 |
| POST | `/auth/validate` | Check whether a token is valid | – | 200 |
| POST | `/auth/logout` | Revoke a token | – | 200 |

### POST /auth/login
Body: `{"username": string, "password": string}`. The only account is `admin` / `password`.

| Status | When |
|---|---|
| 200 | Credentials match. Empty body, `Set-Cookie: token=...; Path=/` |
| 403 | Wrong username or password (empty body) |
| 400 | Missing or malformed JSON body |

```sh
curl -i -X POST http://localhost:3004/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"password"}'
```

### POST /auth/validate
Body: `{"token": "<value>"}`. The token goes in the **body**, not a cookie.

| Status | When |
|---|---|
| 200 | Token exists (empty body) |
| 403 | Unknown or revoked token |

### POST /auth/logout
Body: `{"token": "<value>"}`.

| Status | When |
|---|---|
| 200 | Token deleted |
| 404 | Token not found (already logged out, or never existed) |

> ⚠️ The UI proxy's `POST /api/auth/logout` returns `{"success":true}` **without calling this endpoint**, so the token stays valid. Verified: `/auth/validate` still returned 200 after a proxy logout.

## 5. room

| Method | Path | Purpose | Auth | Success |
|---|---|---|---|---|
| GET | `/room/` | List rooms, optionally only those free for a date range | – | 200 |
| GET | `/room/{id}` | Get one room | – | 200 |
| POST | `/room/` | Create a room | ✔ | 201 |
| PUT | `/room/{id}` | Replace a room | ✔ | **202** |
| DELETE | `/room/{id}` | Delete a room | ✔ | **202** |

### Room object

| Field | Type | Rules |
|---|---|---|
| `roomid` | int | Set by the server; ignored on input |
| `roomName` | string | Required, not empty. Not unique: duplicates are accepted |
| `type` | string | Required; exactly `Single`, `Double`, `Twin`, `Family` or `Suite` (case-sensitive) |
| `accessible` | boolean | Defaults to `false` |
| `roomPrice` | int | 1–999 |
| `image` | string | Optional (e.g. `/images/room1.jpg`) |
| `description` | string | Optional |
| `features` | string[] | Optional; free text (seed data uses `TV`, `WiFi`, `Safe`, …) |

```json
{"roomName":"901","type":"Single","accessible":true,"roomPrice":100,
 "image":"/images/room1.jpg","description":"Quiet room","features":["TV","WiFi"]}
```

### GET /room/
Query: `checkin`, `checkout` (both `YYYY-MM-DD`, optional). Response: `{"rooms":[Room,...]}`.

- **Without dates:** all rooms.
- **With both dates:** all rooms minus those that `GET /booking/unavailable` reports for the range. If you send only one of the two dates, it's ignored and you get all rooms.

> ⚠️ **Availability misses partial overlaps.** A room only drops out of the list if one of its bookings lies **entirely inside** the requested range (see [`/booking/unavailable`](#get-bookingunavailable)). For example, room 1 is booked 2026-02-01 → 02-05, yet a search for 02-03 → 02-04 still lists it as free.

### GET /room/{id}

| Status | When |
|---|---|
| 200 | Room object |
| ⚠️ 500 | Room doesn't exist. The code intends `404`, but the lookup throws first. |
| 404 | Non-numeric id |

### POST /room/

| Status | When |
|---|---|
| 201 | Created; body is the room with its new `roomid` |
| 400 | Validation failure (bad `type`, price outside 1–999, missing `roomName`) |
| 403 | Missing or invalid token (and a valid body) |

```sh
curl -X POST http://localhost:3001/room/ -H 'Content-Type: application/json' -H "Cookie: token=$TOKEN" \
  -d '{"roomName":"901","type":"Single","accessible":true,"roomPrice":100,"features":["TV"]}'
```

### PUT /room/{id}
Full replacement: send every field, because omitted ones are cleared.

| Status | When |
|---|---|
| 202 | Updated; body is the updated room |
| 400 | Validation failure |
| 403 | Missing or invalid token |
| 404 | Room doesn't exist |

### DELETE /room/{id}

| Status | When |
|---|---|
| 202 | Deleted (empty body). The room's bookings are **not** deleted. |
| 403 | Missing or invalid token |
| 404 | Room doesn't exist |

## 6. booking

| Method | Path | Purpose | Auth | Success |
|---|---|---|---|---|
| GET | `/booking/` | List bookings (all, or for one room) | ✔ | 200 |
| GET | `/booking/{id}` | Get one booking | ✔ | 200 |
| POST | `/booking/` | Create a booking (what guests do on the site) | – | 201 |
| PUT | `/booking/{id}` | Replace a booking | ✔ | 200 |
| DELETE | `/booking/{id}` | Delete a booking | ✔ | **202** |
| GET | `/booking/summary` | Booked date ranges for a room, without guest details | – | 200 |
| GET | `/booking/unavailable` | Rooms with a booking inside a date range | – | 200 |

### Booking object

| Field | Type | Rules |
|---|---|---|
| `bookingid` | int | Set by the server |
| `roomid` | int | ≥ 1. **Not checked against existing rooms**: `roomid: 999` is accepted |
| `firstname` | string | Required, 3–18 characters |
| `lastname` | string | Required, 3–30 characters |
| `depositpaid` | boolean | Defaults to `false` |
| `bookingdates.checkin` | date `YYYY-MM-DD` | Required; must be before `checkout` |
| `bookingdates.checkout` | date `YYYY-MM-DD` | Required |
| `email` | string | Optional; if present, must be a valid email |
| `phone` | string | Optional; if present, 11–21 characters |

```json
{"roomid":1,"firstname":"James","lastname":"Dean","depositpaid":true,
 "email":"james@example.com","phone":"01234567890",
 "bookingdates":{"checkin":"2027-06-01","checkout":"2027-06-04"}}
```

### POST /booking/
Response (201): `{"bookingid":4,"booking":{...the booking...}}`.

| Status | When |
|---|---|
| 201 | Created |
| 400 | Field validation failure, or a date in the wrong format (e.g. `01/01/2028`) |
| 409 | `checkin` is on or after `checkout`, or the dates clash with another booking for the same room |
| ⚠️ 500 | `bookingdates` object missing entirely |

**Side effect:** if **both** `email` and `phone` are given, the booking service also posts a message ("You have a new booking!") to the message service, so it appears in the admin inbox. With only one of them, no message is created.

**Date rules (observed):**
- **Past dates are accepted.**
- ⚠️ **Clash detection is asymmetric.** Suppose room 1 is booked 2026-02-01 → 02-05:
  - A new booking that **starts** on 02-05 (the existing checkout day) is accepted.
  - A new booking that **ends** on 02-01 (the existing checkin day) is rejected with 409.
  - Any real overlap is rejected with 409.

### GET /booking/
Query: `roomid` (optional). Response: `{"bookings":[Booking,...]}`.

| Status | When |
|---|---|
| 200 | List (all bookings, or only that room's) |
| 403 | Missing or invalid token |

### GET /booking/{id}

| Status | When |
|---|---|
| 200 | Booking object |
| 403 | Missing or invalid token |
| 404 | Booking doesn't exist |

### PUT /booking/{id}
Full replacement; same body and rules as POST. Response (200): `{"bookingid":..,"booking":{..}}`.

| Status | When |
|---|---|
| 200 | Updated |
| 400 | Validation failure |
| 403 | Missing or invalid token |
| 404 | Booking doesn't exist |
| 409 | Bad dates, or a clash with a booking |

> ⚠️ **A booking clashes with itself on update.** A PUT that keeps the booking's current dates, or overlaps them, returns 409, because the clash check doesn't exclude the booking being updated. Changing only the guest's name fails unless the dates also move to a free range.

### DELETE /booking/{id}

| Status | When |
|---|---|
| 202 | Deleted (empty body) |
| 403 | Missing or invalid token |
| 404 | Booking doesn't exist |

### GET /booking/summary
Query: `roomid` (**required**). Public: this is what the room calendar uses to grey out booked dates.

Response: `{"bookings":[{"bookingDates":{"checkin":"..","checkout":".."}}]}`. Note the field is `bookingDates` here, unlike `bookingdates` everywhere else.

| Status | When |
|---|---|
| 200 | Date ranges (empty list for an unknown room) |
| 400 | `roomid` missing |

### GET /booking/unavailable
Query: `checkin`, `checkout` (both **required**, `YYYY-MM-DD`). Used by `GET /room/?checkin=&checkout=`.

Response: `[{"roomid":2}, ...]`. These are the rooms that have a booking with `checkin >= <checkin>` **and** `checkout <= <checkout>`, i.e. **entirely inside** the range. Partial overlaps aren't returned, which causes the availability bug in [room](#get-room).

| Status | When |
|---|---|
| 200 | List (may be empty) |
| 400 | A parameter is missing |
| 500 | A date can't be parsed (e.g. `checkin=x`) |

|---|---|---|---|---|
| GET | `/branding/` | Get the hotel's branding | – | 200 |
| PUT | `/branding/` | Replace the branding | ✔ | **202** |

### Branding object

| Field | Type | Rules |
|---|---|---|
| `name` | string | Required, 3–100 characters; letters, spaces and `&` only |
| `logoUrl` | string | Required; must be an **absolute** URL (`https://...`) |
| `description` | string | Required, 3–500 characters; letters, spaces and `, & .` only |
| `directions` | string | Required, not blank |
| `map.latitude` / `map.longitude` | number | Required |
| `contact.name` | string | Required, 3–40 characters; letters, spaces and `&` only |
| `contact.phone` | string | Required, not blank |
| `contact.email` | string | Required, valid email |
| `address.line1`, `line2`, `postTown`, `county`, `postCode` | string | All required, not blank |

### PUT /branding/

| Status | When |
|---|---|
| 202 | Updated; body is the new branding |
| 400 | Validation failure |
| 403 | Missing or invalid token |

> ⚠️ **The seed data fails its own validation.** The default `logoUrl` is `/images/rbp-logo.jpg`, a relative path, so `GET` then `PUT` of the unchanged object returns `400 Url should be a correct url format`. Change `logoUrl` to an absolute URL first. The default description also contains characters outside the allowed set, so check it if you resend it.

## 9. report

| Method | Path | Purpose | Auth | Success |
|---|---|---|---|---|
| GET | `/report/` | Every booking, with guest name and room, for the admin calendar | ✔ | 200 |
| GET | `/report/room/{id}` | Booked ranges for one room, anonymised | – | 200 |

Response shape for both: `{"report":[{"start":"2026-02-01","end":"2026-02-05","title":"..."}]}`.

### GET /report/
`title` is `"<first> <last> - Room: <roomName>"`.

| Status | When |
|---|---|
| 200 | Report |
| 400 | No `token` cookie at all (the cookie is a required parameter) |
| ⚠️ 500 | Cookie present but invalid. The booking service answers 403 and the report service doesn't handle it. |

### GET /report/room/{id}
`title` is always `"Unavailable"`. An unknown room id returns 200, listing any bookings made with that `roomid`.

## 10. UI proxy (`/api/<service>`) differences

The website calls the APIs through Next.js at `http://localhost:3003/api/...`. Some paths have custom handlers that **change** the request or response. The others are passed straight through to the service.

| Proxy call | Difference from the direct service |
|---|---|
| `POST /api/auth/login` | Returns `{"token":".."}` in the body. Bad credentials → **401** `{"error":"Invalid credentials"}` |
| `POST /api/auth/logout` | ⚠️ Returns `{"success":true}` but **does not revoke** the token |
| `POST /api/auth/validate` | Valid → `{"valid":true}`; no token → 401 |
| `GET /api/booking?roomid=` | No cookie → **401** `{"error":"Authentication required"}`; no `roomid` → **400**; invalid token → **500** `[]` |
| `GET /api/booking/summary` | Requires the cookie (401 without), though the service itself is public |
| `POST /api/booking` | Validation errors come back as `{"errors":[..]}`; success returns the booking object without the `bookingid` wrapper |
| `POST /api/room`, `POST /api/message`, `PUT /api/branding` | Success → **200** `{"success":true}`, not the created or updated object or 201/202 |
| `GET /api/message` | Public, as on the service |
| `GET /api/report` | No cookie → 401 |

> ⚠️ **Local deployment issue: proxied URLs with an id or sub-path return 500.** Examples: `/api/room/1`, `/api/message/1`, `/api/report/room/1`, `/api/booking/unavailable`, and the Swagger UI under `/api/<svc>/swagger-ui`. The prebuilt UI image was compiled with its pass-through rewrites pointing at `http://localhost:300x`, which inside the container doesn't reach the services (`ECONNREFUSED 127.0.0.1:3005` in `docker compose logs rbp-assets`). The same URLs return 200 on the public demo. Admin features that use them (room detail/edit/delete, opening a message, the room calendar) are likely affected locally. **Call the direct ports for API testing.**
